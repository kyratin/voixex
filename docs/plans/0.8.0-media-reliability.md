# 0.8.0 media reliability implementation plan

Goal: remove avoidable media work and long packet queues, preserve quiet speech and interoperability, and publish validated clients and a dual-architecture server image.

## Ordered implementation

1. Preserve the capacity audit and reusable load tools. Add regressions around quiet speech, silence, self-exclusion, custom gain, congestion, and recovery from pauses.
2. Add conservative silence admission with a hangover. Stop mixing/encoding silence; preserve quiet speech and correct talkspurt behavior. Negotiate optimizations so old peers continue working.
3. Compute a shared unclipped room sum with self-subtraction and sparse per-listener gain corrections. Share encoder work only among truly identical recipient mixes/configurations; retain safe independent stream/talkspurt semantics.
4. Add age/size bounds, audio/control priority, whole-camera-frame admission, and bounded WebSocket worker IPC. Discard stale work before it consumes another codec/network stage. Expose drops/deadlines in diagnostics.
5. Negotiate compatible media demand instead of sending voice and JPEG unnecessarily alongside WebRTC. Preserve immediate fallback and mixed old/new-client rooms. Tie remote video subscriptions to visible main/mini/pop-out ownership.
6. Rework adaptive speaker buffering with bounded latency and stable sample rate. Keep conservative recovery under jitter; test smaller stable-network targets rather than blindly lowering all thresholds.
7. Isolate password hashing in a bounded worker pool so successful login bursts do not monopolize the API event loop.
8. Run functional, browser, congestion, loss, and before/after load checks, including open quiet microphones. Build and validate server images on linux/amd64 and linux/arm64.
9. Publish English release notes and Android/macOS/Windows client installers. Publish the server to Docker Hub with version and latest tags pointing at the same multiarch index. Verify the artifacts and the deployment rollout if updating the existing authorized cluster.

## Architectural boundary

This release preserves one owner for a media room; it does not pretend that increasing replicas or CPU allocation shards a room. Cross-worker room routing/session migration and distributed SFU/control state are a separate architectural milestone. The current one-CPU production node cannot benefit from a larger media worker pool. Re-measure the optimized core before deciding whether/where room sharding is the next bottleneck.

No claim of physical Android/Wi-Fi certification or unlimited simultaneous speakers will be made from synthetic tests.
